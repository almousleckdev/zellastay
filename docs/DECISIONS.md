# Architecture Decision Records

Accepted decisions that shape the architecture. New or changed decisions are appended (never silently rewritten); superseded entries are marked. Open questions live in [OPEN_DECISIONS.md](OPEN_DECISIONS.md).

| ID | Decision | Status |
|---|---|---|
| ADR-1 | Modular monolith (Spring Modulith), one deployable, one PostgreSQL database; no microservices | Accepted |
| ADR-2 | Single Gradle project (Kotlin DSL, version catalog), package-per-module under `com.zellastay`, boundaries verified by Spring Modulith and ArchUnit; Java 21 toolchain; current Spring Boot 4.x line (see ADR-21) | Accepted |
| ADR-3 | Monorepo (`backend/`, `apps/*`, `packages/*`, `infra/`, `docs/`) with path-filtered CI; web apps share workspace packages but deploy independently | Accepted |
| ADR-4 | Persistence: JPA/Hibernate for aggregate persistence; jOOQ or JdbcClient for locking SQL, availability updates and complex reads; repository interfaces in the domain layer; domain model and JPA entities may be the same class only when the aggregate is simple and the mapping stays annotation-light, otherwise separate persistence models | Accepted |
| ADR-5 | Outbox first: Spring Modulith JDBC event publication registry as the transactional outbox. Kafka deferred until a trigger in SYSTEM_ARCHITECTURE §7 occurs | Accepted |
| ADR-6 | Geospatial search starts on PostgreSQL (PostGIS preferred; `earthdistance` as fallback) with a dedicated search read model; external search engine only on measured need | Accepted (PostGIS availability on chosen host to confirm) |
| ADR-7 | Tenant isolation: `organization_id` scoping in the application layer + PostgreSQL row-level security as backstop | Accepted (RLS performance to be verified in Phase 0 spike) |
| ADR-8 | Web i18n with `next-intl`, locale-prefixed routes, `fr` default | Accepted |
| ADR-9 | Mobile state management Riverpod with code generation; `go_router`; API client generated from OpenAPI | Accepted |
| ADR-10 | Inventory correctness via database constraints: conditional counter updates (hotel-style) and GiST exclusion constraints (exclusive units); Redis never guarantees exclusivity | Accepted |
| ADR-11 | Money as integer minor units + ISO 4217 currency; per-currency exponent from configuration | Accepted |
| ADR-12 | Payment abstraction by provider adapter + country/method routing; double-entry accounting ledger (mirror, not custody); reconciliation daily; idempotency at three layers | Accepted |
| ADR-13 | Request to Book is approve-then-pay. A request holds no inventory; vendor approval atomically reserves inventory for a configurable payment window; expiry releases the reservation in the same transaction as the status change; in-flight payments get a configurable grace; late successful payments are auto-refunded. No authorization-hold/capture. | Accepted |
| ADR-14 | WebSocket + STOMP with per-user queues only and Redis pub/sub bridging across instances; persistence is authoritative, real-time is best-effort | Accepted |
| ADR-15 | Cross-module integrity: no cross-module foreign keys; typed-ID references; nightly integrity checks | Accepted |
| ADR-16 | REST audience separation by route prefix and filter chain (`public`, customer, `vendor`, `admin`); RFC 9457 problem details; cursor pagination; mandatory `Idempotency-Key` on money/inventory-affecting POSTs | Accepted |
| ADR-17 | `promotion` (codes, vouchers, campaigns) and `loyalty` (points, referrals) are separate modules to keep the dependency graph acyclic (booking → promotion; loyalty → booking, promotion) | Accepted |
| ADR-18 | `onboarding` is subject-agnostic (opaque subject refs); organization and catalog submit cases and react to decision events | Accepted |
| ADR-19 | Subscription state gates only new commerce; confirmed bookings, chat, refunds and reports are never blocked by subscription state | Accepted |
| ADR-20 | **Non-custodial funds flow:** customer collection and vendor settlement are performed by a licensed marketplace payment provider. Zella Stay does not hold customer funds unless counsel confirms in writing it is authorized to (would require a new ADR). Gabon legal and provider validation (L-1) is mandatory before any live transaction. Provider is not selected (OD-18). The ledger is an accounting mirror reconciled to provider settlement reports | Accepted |
| ADR-21 | Pinned Phase 0 stack (single source: `backend/gradle/libs.versions.toml` plus the Spring Boot BOM): Java 21 (toolchain), Gradle 9.6.1 wrapper, **Spring Boot 4.1.2**, **Spring Modulith 2.1.2**, Spotless 8.10.4, ArchUnit 1.4.2; transitively via the Boot BOM: Flyway 12.4, PostgreSQL JDBC 42.7.14, Testcontainers 2.0.5, JUnit 6. Runtime images: PostgreSQL 16, Redis 7. **Rationale:** Boot 4.1 is the current stable line (4.1.2, released 2026-10-22) and the Phase 0 build and test suite verify that it works with Modulith 2.1.2 on Java 21. **Not a rationale:** Spring Boot 3.5 remains a stable, usable line (3.5.16 is the latest 3.5 release per Spring's documentation, published to Maven Central 2026-06-25); this ADR makes no claim that 3.5 is unsupported. Its end-of-support date was not confirmed from Spring's own support page; a third-party aggregator lists 2026-06-30. Re-check the official support policy before each upgrade and before any production launch. Boot 4.2 was still a release candidate and was not used | Accepted |
| ADR-22 | Backend base package `com.zellastay`; every top-level package is a Modulith module (22 incl. `shared`, which is `OPEN`); module `api` packages (and `api.events` subpackages carrying the same `@NamedInterface("api")` name) are the only cross-module surface; `allowedDependencies` in each module's `package-info.java` must equal the contract in MODULAR_ARCHITECTURE §4, enforced by `ModuleStructureTest`; layer and coding rules enforced by ArchUnit, with fixture tests proving each rule detects violations | Accepted |
| ADR-23 | Price validity between request and approval: the request-time price snapshot is honored; a changed price requires explicit customer acceptance before payment is possible. The state-machine representation of the acceptance step (extra state or guarded sub-step of `PENDING_PAYMENT`) is a Phase 2 design task that must update the BOOKING_LIFECYCLE transition table and tests | Accepted (representation pending) |
| ADR-24 | Settlement-beneficiary gating: a vendor organization cannot accept live bookings until its provider-side settlement beneficiary is verified (`pay_beneficiary.status = VERIFIED`). Enforced server-side by the booking creation and vendor approval use cases through a payment API check; the vendor dashboard only reflects it | Accepted |
| ADR-25 | **Centralized error handling is mandatory on every tier.** Backend: RFC 9457 problem+json produced only by one `@RestControllerAdvice` (`ApiExceptionHandler`) and `ApiErrorController` through `ProblemFactory`; typed `ErrorCode`s (module-namespaced enums with fr + en messages) and `ZellaStayException` subclasses; stable codes, localized text, `requestId` in every response and log line; no internal details ever exposed; controllers never catch. Flutter: one translator in `core/network` producing a sealed `Failure` model and shared presentation widgets. Next.js: typed errors in `packages/api-client`, shared error/empty/loading components and error boundaries. Detail: ERROR_HANDLING.md | Accepted (backend implemented and tested) |
| ADR-26 | **Cloudinary is the media and file storage provider** for property images/galleries, videos, verification documents, profile images and other application media. All access is confined to the `media` module (SDK only in `media.infrastructure`); PostgreSQL stores public IDs and metadata, never binaries; signed uploads with server-authorized parameters and server-side verification (including size, because presets cannot enforce it); private files use `authenticated` delivery with short-lived signed URLs; the API secret never leaves the backend; delete/replace/orphan cleanup are first-class. Conditional on the Phase 1 spike (OD-29) and legal item L-18 for identity/business documents. Detail: MEDIA_ARCHITECTURE.md | Accepted (provider verification pending) |
| ADR-27 | **Flutter: Clean Architecture with native platform UI.** Layers `domain`/`data`/`di`/`presentation` per feature; Riverpod for state and DI; strict DRY and small files. iOS renders only Cupertino, Android only Material; all platform-specific UI and branching live in `core/platform_ui` with `ios/` and `android/` implementations behind one abstraction (own thin abstraction rather than a third-party adaptive package, to keep the import rules enforceable). Detail: CUSTOMER_MOBILE.md §2–§3 | Accepted |
| ADR-28 | **Next.js apps share one feature-oriented architecture** (`features/<f>/{ui,hooks,services,api,schemas,types}`), reuse `packages/ui`, `packages/api-client`, `packages/schemas`; strict TypeScript without `any`; files ≤ 300 lines; consistent loading/error/empty/success states. Detail: WEB_ARCHITECTURE.md | Accepted |
| ADR-29 | **Every mandatory standard needs an enforcement mechanism** recorded in STANDARDS_ENFORCEMENT.md (ArchUnit and Modulith for the backend, `infra/scripts/check_standards.py` and later lint/dependency rules for frontends, review for the rest). Each automated rule is proven against violating fixtures. A rule is relaxed only by a new ADR | Accepted |
| ADR-30 | **Identity is built in-house (closes OD-10)** behind `identity.api`; no external authentication platform is the primary identity system. Phase 1 Slice A authenticates by email only (phone/SMS waits for OD-20); sessions are first-class (`ident_session`) so access tokens can be revoked and sessions listed; verification codes and reset links are handed to the `notification` module through an outbound port (`VerificationDelivery`) and never persisted in plaintext or placed in events; breached-password protection starts with a bundled common-password denylist; the first admin comes from a disabled-by-default bootstrap runner; admin MFA is TOTP (RFC 6238). Design: docs/superpowers/specs/2026-11-02-phase1-slice-a-identity-audit-design.md | Accepted |
| ADR-31 | **Access tokens are ES256 JWTs** (key id in the header, audience-bound, no organization or permission claims, ≤ 15 minutes); refresh tokens are opaque, hashed, rotating with reuse detection. ES256 was chosen over EdDSA because the Nimbus EdDSA signer requires the extra Tink library, while ES256 is JDK-native (verified by `SecurityLibrariesTest`). Password hashing is Argon2id (Spring Security crypto with BouncyCastle). The Spring Security web starter is added only with the filter chains (Slice A task A8) so endpoint behavior does not change earlier | Accepted |
| ADR-32 | **Audit trail:** `audit` is a leaf module; privileged actions record inside the caller's transaction and fail closed, security telemetry records best-effort; `audit_event` is monthly-partitioned and append-only (trigger plus runtime-role privileges); hash chaining (OD-17) is not part of Slice A | Accepted |
| ADR-33 | **Minimum entitlement contract:** `subscription.api.EntitlementApi` (`checkLimit`, `isEnabled`, `listingEligibility`) is the only way catalog, organization and inventory ask what a plan allows; callers pass the requested total because usage lives in the owning module. Phase 1 backs it with minimal admin-assigned plan tables (no prices, payment, trial, renewal or seeded plan values; OD-4 stays open). Design section 11 of the Slice A design | Accepted |
| ADR-34 | **Security chains and rate limiting (Slice A).** One Spring Security filter chain per audience (`/api/v1/vendor/**`, `/admin/**`, customer) plus an anonymous chain for the authentication prefixes; each audience chain ends in deny-all and allows only the patterns modules register through `shared.security.AudienceRoutes` (which, with `TokenAudience`, lives in the shared kernel so the audit module can register its admin route without depending on identity). Authentication is a bearer filter that checks signature, audience, expiry and a cached session-usable check (Redis, 30 s, database fallback, never fail-open). Admin sign-in is two steps with a single-purpose, attempt-limited `mfaTicket`; admin tokens carry `amr=mfa` and `/admin/**` requires it. API rate limiting is a fixed-window counter per client address in Redis with a per-instance in-memory fallback (the earlier "token bucket" wording is superseded). `X-Forwarded-For` is trusted (`forward-headers-strategy: framework`), so the backend must only be reachable through a proxy that overwrites it | Accepted |
