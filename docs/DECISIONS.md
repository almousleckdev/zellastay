| ADR-30 | **Identity is built in-house (closes OD-10)** behind `identity.api`; no external authentication platform is the primary identity system. | ADR-31 | **Access tokens are ES256 JWTs** (key id in the header, audience-bound, no organization or permission claims, ≤ 15 minutes); refresh tokens are opaque, hashed, rotating with reuse detection. | ADR-34 | **Security chains and rate limiting (Slice A).** One Spring Security filter chain per audience (`/api/v1/vendor/**`, `/admin/**`, customer) plus an anonymous chain for the authentication prefixes; each audience chain ends in deny-all and allows only the patterns modules register through `shared.security.AudienceRoutes` (which, with `TokenAudience`, lives in the shared kernel so the audit module can register its admin route without depending on identity). Authentication is a bearer filter that checks signature, audience, expiry and a cached session-usable check (Redis, 30 s, database fallback, never fail-open). Admin sign-in is two steps with a single-purpose, attempt-limited `mfaTicket`; admin tokens carry `amr=mfa` and `/admin/**` requires it. API rate limiting is a fixed-window counter per client address in Redis with a per-instance in-memory fallback (the earlier "token bucket" wording is superseded). `X-Forwarded-For` is trusted (`forward-headers-strategy: framework`), so the backend must only be reachable through a proxy that overwrites it | Accepted |

| ADR-48 | **Repository-wide structure rules (single responsibility, nesting, size, duplication).** Ten permanent rules apply to every tier including tests and tooling: (1) one clear responsibility per class and file; (2) at most 280 lines per file (ADR-43); (3) controllers, services, DTOs, entities, exceptions, error codes, validators, configuration and infrastructure are separate; (4) no domain logic in controllers or presentation; (5) test fixtures, configuration and utilities are separate from tests; (6) unrelated classes are never nested to save files; (7) no unnecessary abstractions and no artificial splits of a cohesive responsibility; (8) Clean Architecture, SOLID, DRY, dependency inversion and module boundaries; (9) no duplicated business rules or implementations; (10) tests obey the same rules as production code. Rule 6 is made precise: a nested type is allowed only when it is non-public and belongs to its enclosing class alone (a private result type, a parameter object), nesting is one level deep, and `@ConfigurationProperties` trees may nest public types because they are one binding unit. Rule 1 gains a mechanical proxy: a class in `application`, `web` or `infrastructure` takes at most 10 constructor parameters (a ratchet at today's maximum; review treats 7 or more as a prompt to ask whether the class has more than one responsibility). The ArchUnit `web` rule is deliberately limited to domain ports (interfaces), because web may map the domain value types an application service returns. Enforced by `StructureRules` in `ArchitectureRules`, proven by violating and clean fixtures; the remaining rules are Active (280 lines, layering, boundaries) or Review (responsibility, duplication) in `STANDARDS_ENFORCEMENT.md` | Accepted (2026-11-22) |
