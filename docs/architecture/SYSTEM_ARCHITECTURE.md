# System Architecture

## 1. Context

```
 Customer Mobile (Flutter/Riverpod) ─┐
 Public Website (Next.js)           ─┤  HTTPS REST /api/v1          ┌─ PostgreSQL (system of record)
 Vendor Dashboard (Next.js)         ─┼─ WSS STOMP /ws ──► Zella Stay ├─ Redis (cache, rate limits, pub/sub, locks-lite)
 Admin Dashboard (Next.js)          ─┘   (via edge/CDN/WAF)  Backend ├─ Object storage (S3-compatible: media, documents)
                                          modular monolith           ├─ Payment providers (Airtel, Moov, card PSP)
                                          (Java 21, Spring Boot)     ├─ Notification providers (email, SMS, push)
                                                                     └─ Kafka (introduced only when justified)
```

One backend deployable, one primary PostgreSQL database. Four independent frontends, each built and deployed separately, talking only to the backend API.

## 3. Architectural style

- **Modular monolith** with strict module boundaries enforced by Spring Modulith verification and ArchUnit in CI. Details in [MODULAR_ARCHITECTURE.md](MODULAR_ARCHITECTURE.md).
- **Clean/hexagonal layering inside each module**: `web` → `application` → `domain` ← `infrastructure`. The domain layer has no framework dependencies beyond minimal annotations decided in [CODING_STANDARDS.md](../engineering/CODING_STANDARDS.md).
- **DDD**: each module owns its aggregates, its tables and its language. No module reads or writes another module's tables.
- **Synchronous calls** between modules only through a module's published `api` interface (read-oriented or command facades). **Asynchronous collaboration** via domain events persisted by the outbox in the same transaction as the state change.
- **Server-side authority**: prices, availability, fees, permissions and state transitions are always computed on the server. Clients never send computed money amounts as truth.

## 4. Deployment topology

- Stateless backend instances behind a load balancer, horizontally scalable. Flyway runs as a separate job (or leader-guarded) before rollout; migrations are backward compatible (expand/contract) so rolling deploys work.
- WebSocket traffic terminates on the same application (separate listener port or path) initially; may be split into a dedicated deployment of the same artifact (profile-based) if connection counts demand it. Fan-out across instances goes through Redis pub/sub (§8).
- Scheduled jobs (hold expiry, outbox retry, reconciliation, subscription renewal) use database-backed locking (`SKIP LOCKED` / ShedLock-style) so they are safe on N instances.
- Environments: local (Docker Compose), CI ephemeral, staging, production. Config via environment variables / secret manager only. See [DEVOPS.md](../engineering/DEVOPS.md).
- Object storage: public media behind CDN; private documents (identity, business) in a separate private bucket accessed through short-lived signed URLs.

## 5. Data and consistency principles

1. PostgreSQL is the single system of record. READ COMMITTED default; critical flows use explicit row locks or conditional updates; SERIALIZABLE is not the default (documented exceptions only).
2. Money: `bigint` minor units + ISO 4217 code; never floating point. XAF exponent 0 — exponents come from currency configuration.
3. Time: stored as `timestamptz` UTC; stay dates stored as `date` in the property's local time zone; conversions only at the edges.
4. IDs: UUID (v7, time-ordered) generated by the application; public booking references are separate short human-friendly codes.
5. Every state-changing external effect (notification, webhook to provider, search index update) happens after commit via outbox, never inside the transaction.
6. Optimistic locking (`version`) on aggregates edited concurrently.

## 7. Event-driven communication and outbox

- Modules publish **domain events** (immutable, past-tense, versioned payloads, defined in the publishing module's `api` package).
- Spring Modulith's **event publication registry** (JDBC) stores each event in the *same transaction* as the business change; listeners run after commit (`@ApplicationModuleListener`: async, transactional, own transaction). Unprocessed publications are retried on restart and by a scheduled resubmission job. This is the transactional outbox for in-process consumers.
- Listeners must be **idempotent** (events are delivered at least once). Each listener stores or derives a dedupe key (event id).
- For external side effects with their own retry/ordering needs (notification delivery, provider calls), the consuming module writes its own work-queue rows (e.g., `notification_delivery`) and a worker processes them with backoff and `SKIP LOCKED`. Provider failures affect only the delivery row.
- **Kafka introduction triggers** (any of): an external consumer outside the monolith needs the stream; sustained event throughput or fan-out exceeds what DB-backed registry handles with headroom; a module is extracted to a separate deployable; analytics pipeline requires an event log. When introduced, an outbox relay publishes selected integration events to Kafka; in-process listeners stay unchanged. Until then Kafka is not deployed. Decision record: ADR-5 in [DECISIONS.md](../DECISIONS.md).
- Event naming and schema versioning rules: [MODULAR_ARCHITECTURE.md](MODULAR_ARCHITECTURE.md) §6.

## 8. Scalability

- Stateless app tier scales horizontally; PostgreSQL scales vertically first, then read replicas for search/reporting read models, then partitioning (availability and audit tables by date) as volumes require.
- Hot paths: search (read model + cache + indexes; PostGIS or equivalent for geo `[ADR-6]`), availability check (indexed per-date rows), booking creation (short transactions, row-level locks only on needed unit-date rows).
- Redis: cache for catalog reads (TTL + event-driven invalidation), rate limiting, WebSocket fan-out. Loss of Redis degrades performance but never correctness (locks that guard correctness live in PostgreSQL).
- WebSockets: STOMP simple broker per instance with Redis pub/sub bridging messages across instances, because the external-broker-relay option would add a new infrastructure component (RabbitMQ/ActiveMQ) the stack does not otherwise need. Revisit if connection counts require a dedicated broker. Details in [CHAT_ARCHITECTURE.md](CHAT_ARCHITECTURE.md).
- Backpressure: bounded executors for async listeners and delivery workers; circuit breakers and timeouts on every provider call.
- Search at scale: start with PostgreSQL full-text + geo indexes; introduce OpenSearch/Elasticsearch only when measured need appears (new ADR).

## 9. Multi-country architecture

- A **country** is a configuration aggregate in `platformconfig`: ISO country code, default currency, supported currencies, default and supported locales, time zones, tax rules, required vendor documents, enabled payment methods and providers, service-fee rules, legal text versions, feature flags.
- Properties belong to a country (derived from address, stored explicitly). Organizations are registered in a country (legal entity country).
- Behavior varying by country is expressed as **data plus strategy interfaces** (e.g., `PaymentProvider` per country/method, `TaxPolicy`, `DocumentRequirementSet`), selected by country code. No `if (country == "GA")` in business code.
- Gabon is seeded as the first country by a migration/seed file that is configuration, not application constants.
- Cross-border concerns (customer in country A booking in country B, currency conversion, display currency) are explicitly **out of scope for launch** except that data models store transaction currency and do not assume one currency. `[OD-16]`
- Details: [INTERNATIONALIZATION.md](INTERNATIONALIZATION.md).

## 10. Multi-tenant vendor isolation

- Tenant = vendor **organization**. Every vendor-owned row carries `organization_id`.
- Defense in depth: (1) the authenticated principal carries organization memberships and property scopes; (2) application services receive an explicit `TenantContext` and every repository query for tenant data filters by it (no unscoped finders for vendor data); (3) PostgreSQL **row-level security** policies keyed on a session variable set per transaction as a backstop `[ADR-7]`; (4) automated tests assert that user A of org X cannot read or mutate any resource of org Y across every vendor endpoint (parameterized authorization test suite).
- Admin and support access crosses tenants only through explicit admin-audience endpoints with their own permissions and audit logging.
- Customer data is not tenant-owned; vendors see only the customer data necessary for their bookings (field-level minimization).
- Object storage keys are namespaced by organization; signed URLs are generated per request after an authorization check.

## 11. Failure handling summary

| Failure | Behavior |
|---|---|
| Notification provider down | Delivery rows retry with backoff; failover provider per channel if configured; booking/payment unaffected. |
| Payment provider timeout | Payment stays `PENDING`; status polled/reconciled; webhook idempotent; booking stays `PENDING_PAYMENT` until due time. |
| Redis down | Cache bypass, rate limiting fails safe per endpoint class (auth endpoints fail closed), chat real-time degrades to poll/reconnect. Booking correctness unaffected. |
| App instance crash mid-transaction | Transaction rolls back; unprocessed outbox rows reprocessed. |
| Duplicate client request | `Idempotency-Key` replay returns stored result. |
| DB failover | Connection pool retry; idempotency + outbox guarantee no duplicate effects. |
