# Database Design

PostgreSQL is the system of record. This document defines conventions, per-module table ownership, key constraints, and the integrity mechanisms the design relies on. Column lists are the **logical** model; exact DDL lives in Flyway migrations once implementation begins and must match this document.

## 1. Conventions

| Topic | Rule |
|---|---|
| Naming | `snake_case`; tables prefixed by module (`ident_`, `org_`, `cat_`, `inv_`, `price_`, `book_`, `pay_`, `sub_`, `notif_`, `chat_`, `promo_`, `loy_`, `rev_`, `sup_`, `onb_`, `media_`, `cfg_`, `audit_`, `eng_`, `rpt_`, `search_`) |
| Primary key | `id uuid` (v7) generated by the application |
| Timestamps | `created_at`, `updated_at` as `timestamptz` UTC; stay dates as `date` |
| Money | `<name>_minor bigint` + `currency char(3)` in the same row; checks `>= 0` unless a signed ledger column |
| Enumerations | `text` + `CHECK` constraint (or lookup table when it is configuration); no native Postgres enums (migration friction) |
| Optimistic locking | `version bigint not null default 0` on aggregates edited concurrently |
| Soft delete | Only where legally/operationally required (`deleted_at`); default is state columns (`ARCHIVED`) and explicit retention jobs |
| Tenant column | Vendor-owned tables carry `organization_id uuid not null` (and `property_id` where relevant) |
| Localized text | Content that vendors/admins author in multiple languages uses a `*_translation` table (`entity_id, locale, field columns`), or `jsonb` keyed by locale for small bounded fields; fallback chain defined in [INTERNATIONALIZATION.md](INTERNATIONALIZATION.md) |
| PII | Columns classified (see [SECURITY_ARCHITECTURE.md](SECURITY_ARCHITECTURE.md) §10); sensitive documents never in the database, only Cloudinary public IDs and metadata |

## 2. Cross-module references

Tables never have foreign keys into another module's tables. Cross-module links are typed UUID columns (e.g., `book_booking.property_id`). Consistency is maintained by API checks at write time and events afterwards. Within a module, foreign keys are used freely. Rationale: preserves extraction-readiness and makes ownership explicit. A nightly integrity-check job reports dangling references.

## 3. Tables by module

Key columns only. `+std` = standard columns (id, created_at, updated_at, version where noted).

## 4. Integrity mechanisms (summary)

| Risk | Mechanism |
|---|---|
| Overselling hotel rooms | `inv_availability` counter row per date, conditional `UPDATE ... WHERE total - held - booked - blocked >= :qty`, plus CHECK constraint |
| Double-booking a single unit | GiST exclusion constraint on `(unit_id, daterange)` |
| Duplicate bookings/payments from retries | Unique idempotency keys scoped per actor/payment |
| Duplicate webhooks | Unique `(provider_key, provider_event_id)` |
| Lost updates | `version` optimistic locking |
| Orphan ownership | One ACTIVE owner partial unique index; one live subscription per org partial unique index |
| Ledger imbalance | Balanced-transaction constraint + verification job |
| Cross-tenant leakage | `organization_id` filters + RLS backstop |
| Audit tampering | Append-only privileges, hash-chaining optional `[OD-17]` |

Required extensions: `btree_gist`, `pgcrypto` (or app-level UUID), PostGIS (or `earthdistance`) `[ADR-6]`, `pg_trgm` for fuzzy search.

## 5. Migrations

Flyway, versioned, forward-only, reviewed. Expand/contract for destructive changes. Single Flyway location `backend/src/main/resources/db/migration`; file names are `V<yyyyMMddNNNN>__<module>_<description>.sql` (timestamp versions avoid merge conflicts; the module prefix states ownership). Modules never edit each other's migrations. The Modulith outbox table `event_publication` is created by `V202611010001__platform_event_publication.sql` (completion mode `update`, schema initialization disabled). Seed data for reference/config (countries, currencies, locales, amenities, default templates, plan seeds) lives in dedicated seed migrations marked as configuration, never as test data in production paths. Production contains no randomly generated or dummy data.

## 6. Retention and deletion

Retention classes (financial records, audit logs, chat, identity documents, PII) and deletion/anonymization workflows are specified in [SECURITY_ARCHITECTURE.md](SECURITY_ARCHITECTURE.md) §10 with durations marked `[LEGAL]` until validated. Financial and audit records are never hard-deleted by user-initiated erasure; personal fields are anonymized where law permits.

## 7. Core domain model summary

Aggregates and their invariants (the authoritative list for implementation):

| Aggregate | Root | Key invariants |
|---|---|---|
| Account | `Account` | Unique verified email/phone per kind; kind immutable |
| Organization | `Organization` | One active owner; cannot approve without approved verification case |
| Property | `Property` | Not publishable unless approved; booking mode ∈ allowed by plan |
| UnitType / Availability | `UnitType`, per-date counters | Held+booked+blocked ≤ total |
| Rate plan | `RatePlan` | Rules non-overlapping per priority; currency fixed |
| Quote | `Quote` | Immutable; expires |
| Booking | `Booking` | State machine; totals consistent; snapshots immutable |
| Payment | `Payment` | Terminal states immutable; amount ≤ booking total |
| Refund | `Refund` | Sum of refunds ≤ payment amount |
| Subscription | `Subscription` | One live per org; state machine |
| Conversation | `Conversation` | One per booking; participants derived from booking |
| Notification | `Notification` + deliveries | Dedupe key unique |
